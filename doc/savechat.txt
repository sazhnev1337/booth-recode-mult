ЧАСТЬ 1. ТЕМА И АРХИТЕКТУРА
================================================================================

Базовая идея: статья Zhu, Li, Song (Microelectronics Journal 157, 2025) —
Radix-4 Booth recoding с zero-skipping. Точный ER4RM (паттерны 00100, 11011)
и приближённые AR4RM1/2 (плюс 00101, 00110, 11001, 11010, ED=±1).

ПУТЬ ИССЛЕДОВАНИЯ (по веткам и итерациям):

1) Прямая адаптация (ветка main, теперь архивная):
   - Параллельный R4 Booth 16x16 с recoder'ами ВНУТРИ умножителя.
   - Level A: 4 пары (k=0..3), каждая покрывает позиции (2k, 2k+1).
     Окно 5 бит a_ext[4k+4:4k]. Recoder проверяет паттерн на нижнем 5-битном
     подокне, верхнее игнорирует.
   - Level B (priority encoding): 4 чётных + 3 нечётных пар (l=0..2, окна
     a_ext[4l+6:4l+2]). Нечётные включаются через enable=~pd_even[l]&~pd_even[l+1].
     Приоритет чётным. КОНСЕРВАТИВНОЕ правило: нечётная approx только если
     lg+1 < APPROX_PAIRS.
   - Zeroed PPG: маска (one|two)?magnitude:0 ДО инверсии, neg_eff=neg&(one|two)
     в neg_correction. Решает проблему all-ones строк (при triplet=111,
     neg_raw=1).
   - Результаты main: лучшая точка approx_4_z в gauss_slow дала -8.8% мощности
     vs baseline. Level B оказался ХУЖЕ level A в fast-сценариях (overhead
     арбитража). Negative result.

2) Текущая ветка external-recoder (АКТИВНАЯ):
   - Идея научного руководителя: recoder ВЫНЕСЕН наружу умножителя,
     амортизация по N тапам фильтра. В регистре умножителя хранится
     УЖЕ recoded-вектор (24 бита: {two[7:0], one[7:0], neg[7:0]}).
   - Three modules:
     * mult_naive — просто a*b (Yosys сам синтезирует)
     * mult_booth — R4 Booth с booth_encoder ВНУТРИ
     * mult_booth_extrec — без encoder, принимает 24-bit recoded
   - Recoder реализован в Python (py/booth_recoder.py), последовательный
     алгоритм со всеми 7 паттернами, как в статье. Правило:
     approx_allowed=(i<approx_until), approx_until=2*N, без условия про i+1
     (статья-стиль).

ЧАСТЬ 3. КЛЮЧЕВЫЕ ИНСТРУМЕНТЫ И ГРАБЛИ
================================================================================

ИНСТРУМЕНТЫ:
- Yosys 0.62+93
- Icarus Verilog 12.0
- OpenSTA 3.1.0 (standalone, без OpenROAD)
- Nangate45 liberty + Verilog cell models из OpenROAD-flow-scripts

ГРАБЛИ:
- Yosys 0.62 НЕ поддерживает строковые параметры через -chparam. Только
  числовые литералы. Пример: -chparam DUT_TYPE 0 (а не "BASELINE").
- DFF_X1/DFF_X2 в NangateOpenCellLibrary.v требуют ручного добавления
  reg Q; reg QN; (Q и QN там объявлены как wire, но присваиваются в
  always-блоке — Icarus падает). DFFR_X1/X2 и DFFS_X1/X2 — только reg Q;
  (QN там через assign).
- cells_adders.v и cells_latch.v НЕ подключать в Icarus — это techmap-правила
  Yosys, не симуляционные модели.
- $value$plusargs работает: vvp file.vvp +STIM=path → читается в reg-string
  через $value$plusargs("STIM=%s", path). reg [8*64-1:0] для буфера пути.
  ВАЖНО: переменную объявлять СНАРУЖИ initial, не внутри. Был баг где
  переменная объявлялась внутри, и значение терялось — тестбенч молча
  использовал default.
- OpenSTA read_vcd работает, scope синтаксис tb_module/dut. Сначала был
  баг где разные VCD давали одинаковую мощность — причина оказалась в том,
  что $value$plusargs не доходил до тестбенча (правки не сохранялись), и
  все три VCD физически содержали одинаковые данные (отличался только
  $date в заголовке, поэтому md5 разный, но tail -n +20 | md5sum одинаковый).
- В netlist после Yosys top-модуль называется ИМЕНЕМ RTL-модуля
  (mult_naive, mult_booth, mult_booth_extrec), а не именем конфигурации.
  link_design должен получать имя модуля.

YOSYS SYNTH PIPELINE:
  read_verilog ... → hierarchy -check -top X → proc → opt -full → techmap
  → opt -fast → flatten → dfflibmap -liberty lib → abc -liberty lib
  → opt_clean -purge → setundef -undriven -zero → stat → write_verilog

OPENSTA POWER:
  read_liberty → read_verilog netlist → link_design → read_sdc
  → read_vcd -scope tb_X/dut → report_power → exit
  Запуск: sta -no_init -no_splash script.tcl
  Команда report_activity_annotation покажет vcd/unannotated splits.

================================================================================
ЧАСТЬ 5. ПРИЧИННЫЙ АНАЛИЗ (для презентации)
================================================================================

ИСТОЧНИКИ ЭКОНОМИИ МОЩНОСТИ:
A) Убран encoder из критической мощности — главный вклад в fast-сценариях
   (-8% в uniform_fast vs -3.6% в gauss_slow).
B) Регистр коэффициента стабилен в slow-сценариях — переключения только
   при обновлении (~раз в 50-1000 тактов).
C) Recoding добавляет занулённых строк в PP-матрицу → меньше переключений
   в дереве сумматоров. +2% (exact) до +5% (approx_2) поверх A+B.

ПОЧЕМУ approx > exact: approx-детектор живёт в Python (снаружи), не вносит
penalty в умножитель. Чистый выигрыш от занулений без overhead.

ПОЧЕМУ gauss даёт меньшую ошибку: малые b → малые |ED·b·4^i|.

ПОЧЕМУ SNR для gauss НИЖЕ uniform: signal² падает быстрее noise² при
переходе к gauss. Не значит худшую точность в абсолюте, просто отношение
к меньшему сигналу.

1) NAIVE СИНТЕЗ слишком большой. Yosys+ABC не оптимизируют как Synopsys.
   РЕШЕНИЕ: убрать naive из основной картины. Упомянуть одной фразой в тексте.

2) ВЫХОДНЫЕ РЕГИСТРЫ не должны входить в мощность умножителя.
   РЕШЕНИЕ (отложено): через wrapper позже. Пока оставляем как есть.

3) ДОБАВИТЬ СЦЕНАРИЙ С update_period=1000.
   ПРОБЛЕМА: при N=10000 sample получится только 10 обновлений `a`.
   РЕШЕНИЕ: пользователь сам прогонит длительную симуляцию с большим N,
   параллельно делается презентация. Sample b всегда меняется каждый такт,
   статистика мощности в основном от потока b.
